  A platform that forecasts daily sales for 30,490 Walmart products,
  runs on any Kubernetes (local kind/k3d + a k3s VPS provisioned with
  OpenTofu), retrains itself with Airflow when drift is detected, and
  deploys new models with GitOps canary releases – fully automated
  from data to production, with zero dependence on a public cloud.

---------------------------------------------------------------------
1. BUSINESS PROBLEM
---------------------------------------------------------------------
A retailer must decide every day how many units of each product to
send to each store. Too few -> stockout (lost sales, angry customers).
Too many -> overstock (money stuck in inventory, waste).
DemandOps forecasts the next 28 days of sales for every item x store,
every night, and feeds a simple reorder policy.

Key business metrics you will report:
  - Forecast accuracy: WRMSSE (official M5 metric), MAE, bias
  - Simulated stockout rate and overstock cost vs. a naive policy
  - Platform metrics: pipeline success rate, time from new data to new
    model in production, serving latency p95, cost per month

2. DATASETS
---------------------------------------------------------------------
PRIMARY – M5 Forecasting Accuracy (Kaggle competition, Walmart data)
  URL      kaggle.com/competitions/m5-forecasting-accuracy
  Size     30,490 item x store series, 1,941 days (2011-2016),
           3 states, 10 stores, 3 categories, ~3,000 products
  Files
    sales_train_evaluation.csv  daily unit sales (wide: d_1 ... d_1941)
    calendar.csv                dates, events, holidays, SNAP days
    sell_prices.csv             weekly price per item x store
  Download: `kaggle competitions download -c m5-forecasting-accuracy`
  If Kaggle is blocked: use a VPN/proxy ONCE, or the copy linked from
  the official M5 repo (github.com/Mcompetitions/M5-methods). Then
  `dvc push` it to MinIO – after that the pipeline NEVER needs the
  internet for data again.

WHY THIS DATASET IS PERFECT FOR MLOPS
  It is a long time series, so we can REPLAY it as if it were live:
  a "data simulator" releases one new day of sales into the landing
  bucket every N minutes. This gives us real daily pipelines, real
  drift (holidays, price changes, trend), and real retraining – without
  needing a company.

DATA VERSIONING
  data/raw/m5/*.csv              -> dvc add (remote: MinIO / S3)
  landing/ (replayed daily files) -> MinIO bucket demandops-landing
  features/*.parquet             -> Feast offline store (partitioned by date)

4. ML PART (keep it simple and correct)
---------------------------------------------------------------------
Step 1 – Data validation (Great Expectations suite or pandera)
  - no negative sales, prices > 0, every series has today's row,
    calendar has no gaps. Pipeline STOPS and alerts if a check fails.

Step 2 – Features (pure functions, unit-tested, registered in Feast)
  - lags: sales lag 7, 14, 28
  - rolling: mean/std over 7, 28, 56 days (shifted by 28 to avoid leak)
  - price: current price, price change vs. last week, price vs. item mean
  - calendar: day of week, month, event type, SNAP flag per state
  - ids: item, dept, category, store, state (categorical)

Step 3 – Models (compare in MLflow, all with the same backtest)
  - Baseline 1: seasonal naive (same day last week)
  - Baseline 2: statsforecast AutoETS on aggregated levels
  - Main: ONE global LightGBM (tweedie objective) over all series
  - Optional: N-HiTS / TFT via neuralforecast (only if time allows)

Step 4 – Backtesting (the most important ML idea here)
  - rolling-origin: 3 folds, each predicts 28 days ahead
  - metrics per fold: WRMSSE, MAE, bias -> logged to MLflow
  - NEVER random split: time series must be split by time

Step 5 – Promotion gates (code in pipelines/gates.py)
  challenger is promoted ONLY if:
    WRMSSE better than champion by >= 1%   AND
    |bias| < 5%                            AND
    p95 latency in staging < 100 ms        AND
    no data-quality failures in the training window
  -> otherwise DAG ends with "kept champion" (logged + Slack/email)

7. MLOPS / CI-CD SPECIFICS (the heart of the project)
---------------------------------------------------------------------
  CI (every PR):    ruff, mypy, pytest (unit + small integration on a
                    100-series sample), GE suite on sample data,
                    docker build, helm lint, tofu fmt/validate/plan
  CD (merge main):  build + push images to Harbor (or GHCR) (tag = git sha)
                    (if GitHub-hosted runners can't reach your server:
                    self-hosted runner inside the cluster via
                    actions-runner-controller, or Gitea + Gitea Actions)
                    -> update helm values in GitOps repo -> Argo CD sync
  Model CD:         retrain DAG opens a PR that changes ONLY the model
                    version in values.yaml -> review -> merge -> Argo
                    Rollouts canary 10% -> 50% -> 100% with automatic
                    rollback on Prometheus analysis (error rate, p95)
  Closed loop:      Evidently drift metric > threshold -> Alertmanager
                    webhook -> Airflow REST API triggers retrain DAG
  Secrets:          External Secrets / sealed-secrets, never in git
  Alerts:           email (SMTP) or a webhook to a messenger bot –
                    no Slack/PagerDuty needed
  Backups:          CloudNativePG backups + MLflow artifacts -> MinIO
                    bucket on a 2nd disk/VPS (restore tested once)
  Cost:             k3d locally for free; 1 VPS for the demo;
                    write the real monthly cost in README

12. WORKING FROM IRAN – SANCTIONS-SAFE SETUP
---------------------------------------------------------------------
REPLACEMENT TABLE (managed cloud service -> self-hosted equivalent)
  AWS S3              -> MinIO (same S3 API: boto3, DVC, MLflow work
                         unchanged) or ArvanCloud Object Storage (S3 API)
  AWS ECR / Docker Hub-> Harbor (own registry, also proxy-cache)
  AWS RDS Postgres    -> CloudNativePG operator (HA + backups to MinIO)
  ElastiCache Redis   -> Redis Helm chart (or Valkey)
  AWS EKS             -> k3s on Iranian VPS / k3d on laptop
  Terraform + registry-> OpenTofu (same HCL language; its registry is
                         not blocked like HashiCorp's downloads)
  AWS Secrets Manager -> sealed-secrets or External Secrets + Vault
  CloudWatch          -> Prometheus + Grafana + Loki
  SageMaker endpoints -> KServe (RawDeployment mode)
  Slack alerts        -> SMTP email / messenger bot webhook
  GitLab.com          -> GitHub (works for Iranian accounts) or a
                         self-hosted Gitea with Gitea Actions

MIRRORS (set up in Week 0, save the configs in infra/mirrors/)
  - Docker images: use an Iranian Docker Hub mirror (several exist,
    e.g. from ArvanCloud and others – check which is alive today) in
    /etc/docker/daemon.json "registry-mirrors" and in k3s/k3d
    registries.yaml. Better: Harbor "proxy cache" project -> every
    image is downloaded ONCE and cached forever.
  - Python packages: pip.conf / uv index-url pointing to an Iranian
    PyPI mirror; fall back to a proxy when one package is missing.
  - Helm charts: `helm pull` charts once, keep .tgz files in the repo
    or push them to Harbor (Harbor is also an OCI chart registry).
  - Models / datasets: download once, store with DVC in MinIO.
  - Keep a short docs/offline-setup.md – it is also a nice portfolio
    document ("air-gapped deployment guide").

HARDWARE / BUDGET
  Laptop k3d: 16 GB RAM is comfortable (use the 100-series sample for
